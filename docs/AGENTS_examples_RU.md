# Базовые примеры AGENTS.md для учебных задач

Все создаваемые агентом документы, планы, статусы, файлы выполнения и отчёты должны быть написаны **на русском языке**. Имена файлов, команд, API и идентификаторов кода переводить не нужно.

## 1. Корневой `AGENTS.md`

```markdown
# Правила проекта

## Язык
- Все Markdown-документы, планы, статусы и handoff пишите на русском языке.
- Имена файлов, команд, API, библиотек, переменных и функций не переводите.

## Источники истины
- `PRODUCT.md` — требования и границы продукта.
- `PLAN.md` — план реализации, зависимости, риски и стратегия тестирования.
- `TASKS.md` — конкретные детали реализации и текущее состояние.
- `docs/agent/tasks/<TASK-ID>/` — отдельные файлы каждой попытки.
- Git и тесты — фактическое состояние и доказательства.

## Перед работой
1. Прочитайте `PRODUCT.md`, `PLAN.md` и `TASKS.md`.
2. Найдите задачу `IN_PROGRESS` и откройте последний файл выполнения.
3. Проверьте `git status`, `git diff` и последние commits.
4. До изменения кода создайте новый файл:
   `docs/agent/tasks/<TASK-ID>/YYYYMMDDTHHMMSSZ_<OWNER>_aNN.md`.
5. Используйте UTC; если имя занято, увеличьте `aNN`. Старые файлы не перезаписывайте.
6. Укажите предыдущий файл и продолжайте с поля «Точный следующий шаг».

## Разделение состояния
- В `PLAN.md` храните стратегию реализации и тестирования, но не текущие статусы и логи.
- В `TASKS.md` храните scope, детали, критерии, владельца, статус, блокер и следующий шаг.
- В файле выполнения фиксируйте команды, результаты, изменённые файлы и `SUBAGENT_HANDOFF`.

## Работа
- Одна небольшая проверяемая задача за итерацию.
- Не меняйте несвязанные файлы и не добавляйте зависимости без одобрения.
- Каждый исполнитель создаёт собственный файл попытки и не перезаписывает чужой.
- Центральный `TASKS.md` обновляет один координатор после проверки diff и тестов.
- Для критичного review по возможности используйте модель другого производителя; результат всё равно подтверждайте тестами.

## Инструменты
- `Context7` используйте, когда нужна документация конкретной версии.
- `grep.app` используйте для поиска примеров в открытом коде.
- `CodeGraph` подключайте, когда важны связи между файлами, символами и вызовами.
- Не подключайте все MCP одновременно: они добавляют инструменты, разрешения и расход контекста.

## Безопасность
- Не выводите `.env`, токены, ключи, персональные данные и закрытый код.
- Skill может содержать исполняемый код: проверяйте `scripts/`, команды, сеть и разрешения.
- MCP подключайте только по необходимости и с минимальными разрешениями.
```

## 2. `src/AGENTS.md`

```markdown
# Правила исходного кода

- Сначала прочитайте корневой `AGENTS.md`, `PLAN.md`, запись задачи в `TASKS.md` и последний файл выполнения.
- Меняйте только файлы, разрешённые текущей задачей.
- Сохраняйте существующий стиль и не проводите дополнительный рефакторинг.
- После изменения запустите относящиеся к задаче проверки.
- Команды, результаты и изменённые файлы запишите в собственный файл выполнения на русском языке.
```

## 3. `tests/AGENTS.md`

```markdown
# Правила тестирования

- Следуйте стратегии тестирования из `PLAN.md` и критериям задачи из `TASKS.md`.
- Для найденной ошибки сначала добавьте воспроизводящий regression-тест.
- Не удаляйте существующий тест только ради зелёного результата.
- Запишите команду, итог и оставшиеся сбои в текущий файл выполнения.
```

## 4. Правила для субагента

```markdown
# Передача подзадачи

- Создайте собственный файл `docs/agent/tasks/<TASK-ID>/<UTC>_<OWNER>_aNN.md`.
- Не изменяйте центральный `TASKS.md` и чужие файлы выполнения.
- Работайте только в заданном scope.
- В конце добавьте `SUBAGENT_HANDOFF`: выполненные критерии, файлы, команды, результаты, блокеры и точный следующий шаг.
- Верните координатору путь к своему файлу; координатор проверяет diff и тесты, затем обновляет `TASKS.md`.
```
