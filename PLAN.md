# PLAN.md

## 1. Этапы реализации и зависимости между ними

**Этап 0. Подготовка инфраструктуры (параллельно, начало дня 1)**  
- Docker Compose (сервисы: backend, frontend, db, nginx, bot).  
- Базовый CI (lint + тесты на push).  
- Репозиторий и структура проекта.  
Зависимости: нет.

**Этап 1. Backend foundation (день 1, утро–день)**  
- Модели данных: User, Family/Group, Member, Transaction, Category.  
- Auth (JWT / session).  
- CRUD семей и приглашений.  
- Эндпоинты загрузки и парсинга CSV.  
Зависимости: Этап 0 (хотя бы каркас Docker).

**Этап 2. Парсинг и базовая логика расходов (день 1, день–вечер)**  
- Парсер CSV (универсальный + 1–2 банка).  
- Правила категоризации и расшифровки названий.  
- Сохранение транзакций с привязкой к семье/пользователю.  
Зависимости: Этап 1 (модели и эндпоинты).

**Этап 3. Frontend MVP (день 1 вечер – день 2 утро)**  
- Страницы: логин/регистрация, создание/присоединение к семье, загрузка файла, дашборд, список операций.  
- Простые графики и таблицы.  
- Ручное редактирование категории/названия.  
Зависимости: Этап 1–2 (API).

**Этап 4. Telegram-бот (день 2)**  
- Авторизация через Telegram.  
- Загрузка файла.  
- Краткая сводка и уведомления.  
Зависимости: Этап 1–2 (общий backend).

**Этап 5. Интеграция, nginx, CI/CD и полировка (день 2 вечер + день 3)**  
- Сборка единого Docker Compose.  
- nginx reverse-proxy.  
- Простой CI/CD pipeline.  
- Улучшение правил / OpenCode-категоризации (если останется время).  
Зависимости: все предыдущие этапы.

**Этап 6. Тестирование и фиксация (конец дня 2 – день 3)**  
- Сквозные сценарии.  
- Исправление критических багов.  
Зависимости: Этапы 1–5.

## 2. Предлагаемые архитектурные решения и ограничения

**Архитектура**  
- Монолитный backend на FastAPI (один сервис).  
- Отдельный процесс/контейнер для aiogram-бота, который ходит в тот же API.  
- Frontend — React SPA.  
- БД — PostgreSQL (или SQLite на время прототипа, если Postgres будет тормозить).  
- Файлы выписок хранятся временно (или в object-storage-like папке) и сразу парсятся.  
- nginx как единая точка входа (статический фронт + проксирование API и бота webhook).

**Ограничения**  
- Никаких платных внешних AI API.  
- AI-логика = набор правил + словари + (опционально) OpenCode / локальные эвристики.  
- Парсинг только CSV.  
- Минимальная модель безопасности: JWT, хэширование паролей, изоляция данных по family_id.  
- Нет горизонтального масштабирования — всё на одном хосте через Docker Compose.  
- Время на инфраструктуру ограничено: шаблоны Docker и nginx готовим заранее.

## 3. Какие модули, данные и интерфейсы потребуются

**Модули backend**  
- auth  
- families (группы + приглашения)  
- transactions (загрузка, парсинг, CRUD)  
- categorization (правила + расшифровка)  
- analytics (агрегации для дашборда)  
- bot_integration (эндпоинты, которые дергает бот)

**Модули frontend**  
- Auth pages  
- Family management  
- Upload  
- Dashboard (суммы + категории + график)  
- Transactions list + edit modal  

**Telegram-бот**  
- /start, привязка аккаунта  
- загрузка документа  
- /summary  

**Данные**  
- User (id, email/telegram_id, password_hash)  
- Family (id, name, invite_code)  
- FamilyMember (user_id, family_id, role=member)  
- Transaction (id, family_id, user_id, date, amount, original_description, cleaned_description, category, source_file)  
- Category (id, name, rules)  
- UserCorrection (для запоминания правок)

**Интерфейсы**  
- REST API (OpenAPI)  
- WebSocket не нужен  
- Telegram Bot API (webhook или long-polling)

## 4. Стратегия unit, integration и ручных проверок

**Unit**  
- Парсер CSV на разных форматах.  
- Правила категоризации и расшифровки (набор тестовых строк).  
- Модели и простые сервисы (создание семьи, добавление участника).

**Integration**  
- Загрузка файла → появление транзакций в БД.  
- Создание семьи → генерация invite_code → присоединение второго пользователя.  
- API дашборда возвращает корректные агрегаты.  
- Бот успешно загружает файл через backend.

**Ручные проверки (обязательные сценарии)**  
1. Регистрация → создание семьи → приглашение → второй пользователь видит данные.  
2. Загрузка тестового CSV → операции появляются → категории проставляются → можно поправить вручную.  
3. Дашборд показывает правильные суммы.  
4. Бот принимает файл и отвечает сводкой.  
5. Всё поднимается одной командой `docker compose up`.

**Тестовые данные**  
- 2–3 заранее подготовленных CSV (разные банки + «грязный» файл).  
- Набор строк для проверки расшифровки («P2P Ivanov I.», «CARD PAYMENT …» и т.д.).

## 5. Критерии завершения каждого этапа

- **Этап 0**: `docker compose up` поднимает все сервисы, CI зелёный на пустой репозиторий.  
- **Этап 1**: можно создать пользователя, семью и получить JWT.  
- **Этап 2**: загрузка CSV создаёт транзакции в БД с категориями по правилам.  
- **Этап 3**: пользователь проходит полный сценарий в браузере без обращения к API вручную.  
- **Этап 4**: бот принимает файл и возвращает текстовую сводку.  
- **Этап 5**: весь стек доступен через nginx, деплой воспроизводим.  
- **Этап 6**: все проверяемые критерии готовности из PRODUCT.md выполнены, критических багов нет.

## 6. Риски реализации и способ отката

| Риск | Вероятность | Влияние | Откат / митигация |
|------|-------------|---------|-------------------|
| Парсер не справляется с реальными CSV | Высокая | Высокое | Зафиксировать 1 универсальный формат + чёткую инструкцию. Отказаться от «магии» банков. |
| Не успеваем сделать качественную AI-категоризацию | Высокая | Среднее | Оставить только правила. AI-часть перенести в «доп. фичи» или вырезать. |
| Docker/nginx/CI съедают слишком много времени | Средняя | Высокое | Использовать готовые шаблоны с первого часа. При критической нехватке времени — запускать сервисы локально без полного CI. |
| Конфликты при работе 7 человек в одном репо | Средняя | Среднее | Чёткое разделение модулей (backend / frontend / bot / infra). Feature-ветки + быстрые ревью. |
| Проблемы с авторизацией Telegram ↔ веб | Средняя | Среднее | В MVP сделать простую привязку по коду или временно разделить пользователей бота и веба. |
| БД или файловое хранилище тормозит | Низкая | Среднее | На прототипе использовать SQLite + локальную папку. |
| Поломка после мержа | Средняя | Высокое | Перед каждым мержем прогонять основные ручные сценарии. Возможность быстрого отката коммита. |

**Общий принцип отката**  
Любую сложную фичу (AI, сложный парсер, продвинутый бот) можно отключить feature-flag’ом или просто не включать в финальный `docker compose`. Основной сценарий «загрузил CSV → увидел расходы в семье» должен оставаться рабочим даже при отключении всего остального.
